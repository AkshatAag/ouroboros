# 9. Shutdown & Process Cleanup

Close keeps the shared daemon; Restart stops this generation's work, then transfers; Panic stops everything before cleanup. A signal proves no exit: a stop requires confirmed death; unconfirmed custody stays for the next start to retry.

### Shutdown doors

| Door | Stops | Keeps | Durable mark |
|---|---|---|---|
| Window close with keep-running on (desktop, live indicator) | nothing: the window hides | every task, schedule, companion and the daemon | none |
| Close, quit, SIGTERM | this generation's workers, services and owned executor/task processes, unfinished reviews included | the shared daemon and its clients; saved pauses; saved work, held for Resume | `server_shutdown.cause`: `external_signal` or `launcher_quit` |
| Planned restart (self-restart, update, rollback) | the same; the daemon only when the landed checkout pins another engine | saved pauses; saved work and the runnable queue, returned; a same-pin daemon | the restart handoff |
| Manual Restart (owner) | the same plus the installation daemon and every delegated run it serves, other clients' included | saved pauses; saved work and the runnable queue, returned | `owner_restart_no_resume.flag` |
| Panic | all owned work; the daemon by confirmed ledger identity | nothing resumes until the owner acts | `panic_stop.flag` |

**Close, quit, Panic (desktop).** `launcher_background.py` decides a window close from `OUROBOROS_DESKTOP_KEEP_RUNNING`, read at that moment: on, with a live indicator (Windows, macOS), the window hides; off, or without an indicator, the close quits through the teardown below; undecided, the first close asks once and stores the answer. A quit (the indicator's Quit, Cmd+Q, sign-out, shutdown) is never asked or cancelled and sets no Panic flag. Panic keeps its own path: the server exits with the Panic code, the lifecycle thread asks the indicator to go without waiting, and the indicator's Panic item posts `/api/command /panic` over loopback, as Android's notification does. A second manual launch shows the running window, even while that copy still boots; Linux keeps the plain close.

Close releases its PID lock; the daemon stays because it serves work beyond one window (Windows keeps it outside the launcher Job; spawn custody and the reaper: §1 Runtime topology). `launcher.stop_agent` signals the server PID only (POSIX SIGTERM; Windows `quit\n` on the owned stdin, `OUROBOROS_LAUNCHER_STOP_STDIN`), waits `LAUNCHER_STOP_GRACE_SEC`, then forces group/Job cleanup; the signal sets the stop latches at once and `SERVER_GRACEFUL_SHUTDOWN_TIMEOUT_SEC` bounds the Uvicorn drain, so custody completes even when the whole group is signalled. `_exit_signalled` is never cleared, so a settings save landing mid-teardown cannot revive a supervisor generation; a fresh lifespan clears `_supervisor_stop` (`server.py`).

### Restart and retention

Teardown sets the stop flag, joins the supervisor within its bound and terminalizes `kill_workers` before optional waits/sweeps; the watcher owns cleanup and handoff. Owned stops share the first door's grace (`owned_shutdown.stop_owned_work`; §10 invariant 6); unconfirmed stops carry `unconfirmed_since` for startup retry before admission. Pin rule: `server_restart._stop_owned_daemon_for_new_pin`; body adoption needs stop evidence (§6). Fresh recovery needs launcher exit 42 or the one-shot token under lock with same-PID exec, custodied POSIX spawn or Windows original-parent HANDLE exit 42 and bound births (venv base, cold-adoption child). Only that successor gets S1 saved-work/queue returns; undispatched owner-wait/planned carriers use the acknowledged transaction through their own gates, also in a later process. Binding failure keeps a custodied server available with unproved work held; Panic still stops it. Restart has no port sweep: ports prove no ownership; launcher, recovery and Panic sweeps may stop unrelated listeners.

Manual Restart (`server_restart._perform_owner_restart`) checks update lock, transaction and `safe_restart` before stopping anything; a refusal (an unwritable no-resume flag too) says "Restart cancelled" and leaves the server intact. It then writes `owner_restart_no_resume.flag` without removing Panic, names returning owner waits, checkpointed work and runnable unstarted queue in one `restart_retention.prepare_restart_returns` transaction, and cancels other live work except saved pauses. Teardown uses `kill_workers(retain_saved_work=True, preserve_pending=True)`, `reconcile_orphaned_runs` with attach-only `read_owned_gateway`, daemon `stop_outcome` and owned stop; never `ensure_owned_gateway` (it could start a dead daemon). Unconfirmed stops retain custody and report `process_stop_unconfirmed`, never veto Restart. No run adoption follows (`owner_restart` is a §6 no-resume cause); owner-gone runs settle from `close_absent_run` or their terminal journal without invented spend.

**Retention.** Every stop keeps saved pauses (`restart_retention.py`, boot reader `queue_snapshot.py`): signal first, park the marker, never terminalize or emit `task_done`; unused Resume grants return to Pause. Post-task remainders stay in `root_phase_checkpoint` without auto-resume (§6). Application stops keep saved work (`retain_saved_work`; return authority: §6 Saved working state). Unnamed rows stay held (`owner_restart_hold`); rows without dispatch evidence stay `dispatch_outcome_unknown`, never called never started. Selectable holds need explicit Resume or model selection under a live root grant; Restart reports their count. Stop beats pauses; `pausing` without a source uses the attempt's working state, else stays interrupted intent (Continue, not exact Resume). Panic needs none of this.

### Panic path

Panic claims termination at ingress; failed thread start calls the executor synchronously. Owned stops (restart successor too) precede I/O/cleanup (BIBLE Emergency Stop Invariant). Diagnostic/manager failures leave other requests intact; bounded-write failure cannot prevent final exit 99. The restart watcher parks; a successor seeing 99 never serves. Workers get a short socket window; the lifeline bounds callbacks, and the parent times its own Popen kill independently. Delivery, request and proven death differ: unpublished spawns, inaccessible owners and backend-only children remain unconfirmed. WS/HTTP uses `LocalChatBridge.panic` without supervisor/state I/O; Host Service authenticates the skill and pinned owner pair (§12). Boot consumes the flag only after disabled controls persist; failure retains it and blocks reviews of newly admitted owner work until Restart persists them.

### Owned daemon stop and startup failure

`OwnedClaudexorDaemon.stop_outcome` (Panic and Restart) returns `stopped`, `nothing_to_stop` or a disclosed `unconfirmed`. Cooperative first: with a valid owned marker and an authenticated same-home endpoint it runs the installed CLI `daemon stop --json` and requires exit 0 plus the typed terminal receipt, because an RPC acknowledgement or a lease release does not prove the OS processes exited; forced signalling then covers only the pre-request custody snapshot and needs measured birth and command identity or the manager's own Popen. Only confirmed death removes custody; a token refusal, invalid discovery or a matching error string grants no stop authority. Lock, RPC and exit waits are bounded separately by `CLAUDEXOR_OPERATOR_STOP_TIMEOUT_SEC` and `CLAUDEXOR_STOP_EXIT_WAIT_SEC` (§7), with no promised total. A live startup outlives its caller's `CLAUDEXOR_STARTUP_WAIT_SEC` window: `daemon_starting` invites joining it, `daemon_not_answering` a live listener that stayed silent, `daemon_spawn_failed` an exited child. The rules a change must keep: DEVELOPMENT "Process Custody Rule".

**Startup failure.** `claudexor_startup_failure.py` labels an owned child's exit without a control endpoint, from its own `daemon.log` interval, as `heap_exhausted`, `writer_lease_contended`, `engine_floor` or `unclassified`; the label is diagnostic, never behavior, carried in the typed `daemon_spawn_failed` detail, `last_error` and one durable `claudexor_daemon_start_failed` row. The latch keys on the typed exit alone; while it is set, every ordinary caller gets an immediate `daemon_spawn_failed` without a spawn, unless a live startup exists, which it joins. Each manager has its own latch, released by a live-daemon attach or a new manager; the server's also by the periodic custody sweep (§5), which makes one zero-wait ensure only when it released a latch, or by the owner's Refresh (`/api/claudexor/wake`), one spawn per press; a worker's needs an attach or worker respawn. Attach, sweep and Refresh releases are rowed as `claudexor_daemon_start_latch_cleared` with `cleared_by`. The host adds no backoff, cooldown or writer-lease handling and derives no heap size from RAM, which only moves the crash; the engine names its own ceiling through probe `launch.nodeArgs` and managed launch passes it as a bounded `--max-old-space-size`. An explicit `NODE_OPTIONS` heap option wins, as the operator's escape hatch; missing or malformed launch data keeps the plain command (`runtime_launch_invalid` in runtime diagnostics). Harvest cadence: DEVELOPMENT "Process Custody Rule"; the two disclosed latch residuals: `claudexor_startup_failure.ExitFact` and `OwnedClaudexorDaemon.clear_start_failure_latch`.

`claudexor_exit_facts.py` reads the engine's recent exit facts (the host's observation time, not the death time) from the bounded tail of `supervisor.jsonl` for context, which never calls the engine. The owned-daemon status read (`/api/claudexor/status`, §4) adds `last_exit` and live `memory` from the already-running endpoint, null when unknown or the engine is old, and records one `claudexor_engine_capacity` row per descriptor generation. These are observations, not lifecycle authority: no heap threshold, notification or restart policy follows.

### Process custody

`_active_subprocesses`, task-attributed executor records (§1) and ledgered task processes are named by `state/owned_processes.json` (a contended registration lands in `owned_processes.pending/`), which exit and Panic read instead of walking `data/state`; a boot side thread indexes older records once. Groups and Jobs miss escaped descendants, so a signal needs the measured identity, and startup recovery settles no executor backend: only stamped stops are retried. Docker CLI exit proves no backend exit: `backend_completed` is persisted before marker deletion, and a lost reply retains evidence, never signalling a completed CLI PID. Host unwind or exact worker death retires the local invocation only (§6); unknown effects never authorize replay.

**Follow-up controls.** An accepted Stop transfers its control identity to the original task result before the active intent retires, also when natural completion wins, so the completed status and result survive; a failed transfer keeps the intent for recovery. A recorded cancel intent wins over the door's cause; an unreadable store invents none. Manual Restart keeps its control in the schedule document before consuming its marker; Panic needs none. Owner: `supervisor/followup_policy.py`.
